# 03 · 협업 흐름

GitHub Flow 를 따른다. `main` 은 항상 배포 가능한 상태를 유지한다.

## 브랜치

- `main` 에 직접 push 하지 않는다. 모든 변경은 브랜치 → PR 을 거친다.
- 브랜치명: `<타입>/<요약>` — 예 `feat/user-loader`, `fix/nan-handling`.
- 타입: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
- 작업 시작: `git switch main && git pull && git switch -c feat/x`.

## 커밋

Conventional Commits.

```text
<타입>: <요약>          # 명령형, 72자 이내

<본문 — 왜 이 변경이 필요한가>
```

## Pull Request

1. `git push -u origin <브랜치>`.
2. `gh pr create --fill --web`. 제목은 커밋과 같은 형식.
3. 템플릿의 변경 내용·배경·확인 방법을 채운다.
4. 리뷰어를 1명 이상 지정한다.
5. CI 통과 + 승인 1개 후 **Squash and merge**. 병합 후 브랜치를 삭제한다.

## 리뷰 기준

- 정확성, 엣지 케이스, 테스트 유무.
- 지적은 구체적으로, 가능하면 대안을 함께 제시한다.
- 반영은 같은 브랜치에 push 한다. PR 이 자동 갱신된다.

## `main` 보호 규칙

- PR 없이 push 금지.
- 병합 전 CI(`quality`, `docker build`) 통과 필수.
- 승인 1개 필수. 새 커밋이 올라오면 이전 승인은 무효화된다.
- `CODEOWNERS`(`@rinaking`)가 기본 리뷰어로 지정된다.
